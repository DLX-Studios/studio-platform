# Studio Project Init

Own whole-project discovery, architecture, and repository structure. Include the project Console web app by default. Use the related Studio skills for specialized work: `studio-app-init` adds nested apps, `studio-console-init` creates or updates the Console, and `studio-design` creates or refines `DESIGN.md`.

Before presenting planning questions or structural choices, read and follow [visual interaction for Studio planning](references/visual-interaction.md). Use available chat controls and visuals to compare the repository shapes, example trees, app targets, and console choices; keep the text choices and the question visible as well.

## Discover and research

- Inspect the project root, existing files, `AGENTS.md`, `STUDIO.md`, manifests, and applicable sibling-project references. For an empty project, use the user's description and environment constraints.
- Identify purpose, intended users, workflows, delivery surfaces, target platforms, data and integrations, privacy/operations constraints, and likely growth needs. Explicitly distinguish browser access from installed mobile/desktop apps; a responsive page does not satisfy an installable-app request. If the user mentions device classes such as phones, tablets, or computers without saying whether installation is needed, ask whether they want browser access, installed apps, or both before recommending a stack. Offer “all of the above” and common combination presets for multi-select delivery choices, plus custom input; do not require the user to enumerate each channel. Preserve useful existing structure in an evolving project.
- Offer all three project shapes with a best-fit description before fixing the layout, unless the user already chose:
  1. **Single application:** one main product/deployable with companion tools. Best when components share a product and release boundary.
  2. **Multi-app/platform workspace:** related runnable apps and shared platform code in one repository, apps under `/apps/{app_name}`. Best when apps share contracts, data, packages, tools, or runtime capabilities. Treat application monorepo and platform workspace as variations of this one option.
  3. **Umbrella of separate repositories:** independently versioned repositories grouped under a parent folder. Best when products need shared discovery or planning but not a shared build graph or coordinated release boundary.
- Classify by product, operation, and release boundaries, not language or binary count. A web app and Rust companion released together may still be one application.
- Conduct a focused research pass before presenting the project plan. Inspect existing project references and shared catalog values; use available web/research tools for relevant domain facts, standards, and comparable projects. Prefer authoritative sources, link them in the plan, and distinguish sourced facts from recommendations.

## Define the project plan

- Keep **domain**, **lifecycle status**, and **application type** as separate catalog fields, independent of repository structure. Projects can have multiple domains and application types but only one current lifecycle status.
- There is no starter domain list. Use research to choose domain value(s), reuse shared values when they fit, and propose a new shared value only when needed. Include domain value(s), rationale, and sources in the plan.
- Start application types with Studio Platform app/plugin, Web app/site, Desktop app, Mobile app, CLI tool, Backend/API service, Background worker, and Firmware/embedded app. Keep the shared list extensible. Use Idea, Planned, Active, Maintenance, Paused, Complete, and Archived as the starting lifecycle values. Do not encode catalog values in folder names.
- In project/app planning, display browser, installed desktop, and installed mobile delivery channels separately beside every app-type choice; then show the likely OS targets. Recommend the Studio Platform app/plugin as the default app profile, including for all-surface goals. If its current host does not yet support one of the selected surfaces, record that gap and ask whether it is a v1 requirement or an accepted roadmap target. Offer SvelteKit + Tauri as an alternate when the user explicitly prefers it or requires those surfaces before Studio Platform support is ready. Record selected `target_platforms` separately from type, implementation, and delivery choice. Label support as supported, limited/experimental, or unverified, and verify framework-specific claims against current authoritative docs. Follow the matrix and Studio Platform / GPUI Kit / SvelteKit + Tauri caveats in root `STUDIO.md`; service targets are deployment environments and firmware targets are concrete boards/architectures.
- For a multi-app workspace, use `/apps/{app_name}` as the language-neutral runnable-app boundary, with native manifests at each app root. Add root `packages/` for shared JS/TS, `crates/` for shared Rust, and other shared folders only for real consumers. Choose root versus nested Cargo workspace from actual build/release boundaries.
- Ensure every app has a root `APP.md` as the canonical metadata brief for the Console catalog, following the schema in root `STUDIO.md`. For nested apps, create both `APP.md` and `AGENTS.md`; the brief records type, implementation, targets, purpose, boundaries, and spec links, while AGENTS gives concise workflow instructions and matching skills. Discover and list matching skills from the current agent's catalog, use `$find-skills` when needed, and read/follow relevant matches. Refer to them by name without machine-specific paths. Route nested-app creation or updates to `studio-app-init` (or `studio-console-init` for the Console). For a single app at the repository root, use root `APP.md` and root `AGENTS.md`; in an umbrella, put both files in each app repository.
- Resolve conflicts using current explicit user decisions and accepted specs/plans first, then project-wide `STUDIO.md`, app-specific `APP.md`, and derived agent instructions. Verify implementation claims from manifests/source/configuration and reconcile stale docs. Treat Console catalog data as an index of `APP.md`; metadata edits must update the canonical brief in the same change.
- Compare independent operation/release boundaries, shared code, runtime needs, ownership, and expected growth. Present a concise brief covering purpose, workflows, major components, boundaries, data flow, folder tree, unresolved choices, and non-goals before broad restructuring. Show illustrative trees for the three project shapes and let the user correct material decisions.
- Include the project Console web app in the default plan, folder tree, and implementation handoff. Do not ask whether the user wants or needs it. Reuse an existing Console and honor an explicit exclusion. Derive its placement from the chosen repository shape, preserving the main product's source layout; pass the product brief, placement, and remaining implementation decisions to `studio-console-init`.
- Check for root `DESIGN.md`. Use an existing guide by default. If missing, gather any high-level appearance direction and references from the user, then call `studio-design` to create it before finalizing the plan. Pass along all collected design context so the user is not asked twice.

## Route implementation and maintain project guidance

- Once the whole-project direction is agreed, implement the project-level structure and docs, route app scaffolding to `studio-app-init`, and invoke `studio-console-init` for the default Console as part of the initialization workflow. Route design-file creation/refinement to `studio-design`. For planning-only requests, include the Console and its implementation handoff in the plan without scaffolding it prematurely.
- Create or maintain one project-root `STUDIO.md` for purpose, architecture, boundaries, and sources of truth. Preserve an established `docs/STUDIO.md` convention and do not create duplicates.
- Keep `README.md` for setup, usage, and contribution guidance. Keep `AGENTS.md` for durable instructions that change how future agents work. Update affected docs and manifests; avoid unrelated moves or broad rewrites.
- Summarize the agreed shape, changed files, assumptions, unresolved decisions, and actual validation. Use `studio-commit` for a separate checkpoint when requested.
